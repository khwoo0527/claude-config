# Verification Before Completion — 완료 선언 게이트

> **한 줄 정의**: 증거 없으면 완료가 아니다. "될 겁니다"는 이 스킬의 실패 판정이다.
> 근거 정책: `rules/workflow/sprint-workflow.md` § 완료 기준 ("빌드 통과 ≠ 완료, 실환경 동작이 완료") + `rules/memory/feedback_test_guide.md` (테스트 가이드 제공).

---

## 절대 원칙

1. **주장 금지, 실증만** — 모든 검증 항목은 실제 명령 실행 + 출력(로그) 확보. 회상이나 "아까 통과했으니까"로 대체 불가 (수정이 하나라도 있었으면 재실행).
2. **완료의 정의는 사용자 기준** — 빌드 통과가 아니라 "사용자가 지금 실행해서 눈으로 확인 가능한 상태 + 뭘 확인해야 하는지 아는 상태"가 완료다.
3. **부분 실패 = 전체 미완료** — 검증 항목 중 하나라도 실패/미실행이면 완료 선언 금지. "대부분 통과"는 없다.
4. **땜빵 금지** — 검증 실패 시 근본 원인 수정 (sprint-workflow § 에러/버그 수정 원칙). 테스트를 약화시켜 통과시키는 것 금지.

---

## 실행 절차

### 1단계: 완료 조건 수집
검증할 항목을 문서에서 모은다 (기억으로 만들지 않는다):
- `docs/sprint/sprint{N}.md`의 "최종 검증 계획" 섹션 (있으면 — 이게 1순위 계약)
- `/CLAUDE.md`의 빌드/테스트/린트 명령
- 이번 작업의 원래 요구사항 (Task 완료 기준)

### 2단계: 전 항목 실행 + 증거 캡처
| 항목 | 통과 기준 |
|---|---|
| 빌드 | 에러 0 (경고는 sprint 문서 기준으로 판단) |
| 린트/포맷 | CLAUDE.md에 명령 있으면 실행, 0 위반 |
| 테스트 | 전원 통과 (0 failures) — 기존 테스트 포함 (회귀 확인) |
| 실행 | 앱/서비스가 실제로 뜨는지 — 크래시 없이 대상 화면/기능 도달 |
| 데이터 흐름 | DB/API/인증이 실환경(또는 스테이징)에서 정상 (해당 시) |

각 항목의 **실제 출력 일부를 결과 보고에 포함**한다 (예: "Build succeeded. 0 Warning(s) 0 Error(s)").

### 3단계: 사용자 테스트 가이드 작성 (생략 불가)
사용자는 눈으로 확인하며 진행하는 스타일 — 가이드 없이 "실행해보세요"는 미완료다:
```
📋 테스트 가이드
- 정상 범위: 여기까지 동작해야 정상입니다 — {범위}
- 확인 순서: 1) {화면/명령} → 2) {조작} → 3) {예상 결과}
- 아직 안 되는 것 (정상): {이번 범위 밖 항목 — 오해 방지}
```

### 4단계: 결과 보고 + 판정
```
| 검증 항목 | 결과 | 증거 |
|-----------|------|------|
| 빌드 | ✅ | 0 errors (출력 요약) |
| 테스트 | ✅ | 12 passed, 0 failed |
| 실행 | ✅ | {화면} 정상 표시 |
→ 판정: 완료 선언 가능 / ❌ 항목 존재 → 미완료 (아래 실패 처리)
```

### 실패 처리
1. 실패 원인 분석 (증상이 아닌 근본 원인) → 수정 → **2단계부터 재실행** (수정했으면 전 항목 재검증)
2. 3회 실패 시: 중단하고 실패 항목 + 시도 내역 + 원인 가설을 보고 (더 파고들지 임의 결정하지 않음)

## 안티패턴 (이 스킬의 실패 판정)

| 안티패턴 | 왜 실패인가 |
|---|---|
| "빌드 통과했으니 완료입니다" | 실행/데이터 흐름 미검증 — 완료의 정의 위반 |
| 출력 없이 "테스트 통과했습니다" | 실증 원칙 위반 — 주장일 뿐 |
| 마지막 수정 후 재검증 생략 | "한 줄 고쳤을 뿐"이 회귀의 주범 |
| 실패 항목 있는데 "나머지는 완료" | 부분 실패 = 전체 미완료 |
| 테스트 기대값을 실패에 맞춰 수정 | 땜빵 — 검증 무력화 |
| 테스트 가이드 없이 "확인해보세요" | 사용자가 뭘 봐야 할지 모름 (feedback_test_guide 위반) |
