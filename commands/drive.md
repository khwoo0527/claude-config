목표 한 줄을 받아 현재 상태를 진단하고, 필요한 단계(PRD→ROADMAP→Phase→Sprint→구현→마무리)를 알아서 체이닝하는 지시자 모드 오케스트레이터.

> **왜 필요한가**: 파이프라인 에이전트들은 훌륭하지만 각각을 사용자가 순서대로 직접 호출해야 했다.
> 이 커맨드는 "무엇을 만들고 싶은지"만 받고, 어디까지 준비됐는지 진단해서 **빠진 단계부터** 자동으로 이어간다.
> 사용자 개입은 감독 레벨([`supervision.md`](../rules/workflow/supervision.md))의 게이트에서만 발생한다.

## 인수

`$ARGUMENTS`: 목표 서술 (자연어) + 선택적 레벨 병기
- 예: `/drive 회원 알림 기능 만들고 싶어` / `/drive L2 결제 모듈 추가` / `/drive` (인수 없음 — 다음 할 일 진단만)

## 실행 절차

### 1단계: 상태 진단 (Read-only)

프로젝트의 현재 위치를 실측한다:

| 확인 대상 | 판정 |
|---|---|
| `/CLAUDE.md` | 없음 → 새 프로젝트 (project-init 필요) |
| `docs/prd.md` | 없음/목표와 무관 → PRD 단계부터 |
| `ROADMAP.md` | 없음 → prd-to-roadmap 필요. 있으면 목표가 기존 Phase 에 속하는지 판정 |
| `docs/phase/phase{N}.md` | 목표가 대규모(다중 스프린트)인데 없으면 phase-planner 필요 |
| `docs/sprint/` 마지막 sprint{N}.md | 미완료 스프린트 존재 시 → 이어서 할지 사용자 확인 |
| git 상태 | 미커밋 변경/브랜치 위치 — 더러운 상태면 보고 후 정리 확인 |

### 2단계: 목표 크기 판정 + 실행 계획 제시

| 목표 크기 | 기준 | 체인 |
|---|---|---|
| **Hotfix 급** | 프로덕션 버그, 파일 3개/50줄 이하 | 바로 수정 → hotfix-close |
| **Sprint 급** | 기능 1개, 기존 Phase 범위 내 | sprint-planner → 【계획 승인】 → /sprint-dev → 【완료 검수】 → sprint-close → 【PR 검토】 → sprint-review → 【머지/수동 검증 승인】 |
| **Phase 급** | 다중 스프린트 규모 신규 영역 | phase-planner → 【Phase 승인】 → Sprint 급 체인 반복 |
| **프로젝트 급** | CLAUDE.md 없음 / 새 제품 | project-init → PRD 인터뷰 → prd-to-roadmap → Phase 급 체인 |

진단 결과와 실행 계획을 한 화면으로 보고:
```
🧭 /drive 진단
현재 상태: {CLAUDE.md ✅ / ROADMAP ✅ Phase 2 진행 중 / sprint4 완료}
목표 판정: "{목표}" → Sprint 급 (Phase 2 범위 내)
실행 계획: sprint-planner 로 sprint5 계획 → 승인 후 L{N} 구현 → close → review
사용자 게이트 (L2 기준): ① sprint5.md 승인 ② 완료 검수 (화면 확인) ③ PR 검토 ④ 머지/수동 검증 승인 — 예상 개입 4회
진행할까요?
```

### 3단계: 체인 실행 (레벨 게이트 적용)

- 각 단계는 **기존 에이전트/커맨드를 그대로 호출** — 이 커맨드는 지휘만 하고 절차를 중복 구현하지 않는다.
- 단계 간 산출물 인터페이스 확인 후 다음 단계로 (예: sprint{N}.md 생성 확인 → /sprint-dev).
- **인터뷰형 단계는 인라인 수행**: project-init·phase-planner·prd-to-roadmap·요구사항 인터뷰처럼 실행 중 사용자 대화가 필요(하거나 전환될 수 있는)한 단계는 서브에이전트로 스폰하지 않는다 — 메인 스레드가 해당 에이전트 문서를 Read 하여 절차 그대로 인라인 수행 (agent-guide.md § 실행 방식 참조). 상호작용 없는 단계(sprint-close 등)는 스폰 가능.
- **게이트 (supervision.md 따름)**:
  - 요구사항이 모호하면 → 인터뷰 (짧게, 핵심만 — 답을 추측으로 채우지 않음)
  - 계획 문서(sprint/phase) 생성 직후 → 사용자 승인 대기 (L0~L2. **L3 은 phase{N}.md 승인만 게이트** — 그 범위 내 sprint 계획은 보고 후 자동 진행)
  - 구현 구간 → 선언된 레벨의 게이트만 적용 (L2: 자동 주행 + 완료 검수)
  - **sprint-close 후 → 사용자 PR 검토 게이트** (sprint-review 의 선행 조건 — L3 은 보고 후 자동 진행)
  - push/메인 병합/배포 → 레벨 무관 사용자 게이트
- 단계 사이 진행 보고 1줄씩 남긴다 (자리 비운 사용자가 돌아와서 흐름 파악 가능하게).

### 4단계: 완료 보고

```
🏁 /drive 완료: {목표}
거쳐간 단계: {체인 요약}
산출물: {sprint5.md, 커밋 N개, PR 링크, deploy.md 갱신 ...}
사용자 개입: {실제 발생 게이트 횟수}
다음 추천: {sprint-review 대기 / 다음 스프린트 후보 ...}
```

## 에러/중단 처리

- **미완료 스프린트 발견**: 이어서(resume) vs 새로 시작 vs 중단 — 선택지 제시 후 진행 (임의 결정 X)
- **체인 중간 단계 실패**: 해당 단계의 에러 처리 규칙 적용 후, 해결 불가 시 어디까지 진행됐고 무엇이 막혔는지 보고하고 정지
- **목표가 기존 ROADMAP 과 충돌**: 자동 재계획하지 않는다 — 충돌 내용 보고 + Phase 재계획 여부 사용자 결정
- **supervision 불변 원칙** (Critical 중단, 스코프 이탈 중단, 3회 실패 중단) 상시 적용

## 동작 원칙

- **지휘자이지 실행자가 아니다** — 각 단계의 절차는 해당 에이전트/커맨드 문서가 진실 원천. 이 문서에 절차를 복제하지 않는다.
- **진단은 실측** — "아마 ROADMAP 있을 것" 금지. 파일 존재/내용 확인 후 판정.
- **개입 최소화, 게이트 명시** — 시작할 때 "예상 개입 N회"를 미리 알려주고, 그 약속을 지킨다.
