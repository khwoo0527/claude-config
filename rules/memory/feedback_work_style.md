## 단계별 진행 (감독 레벨 연동 — 2026-07-03 개정)

진행 단위는 [`rules/workflow/supervision.md`](../workflow/supervision.md) 의 **감독 레벨**을 따른다. 레벨 미선언 시 기본 레벨(L1)로 동작.

**L0~L1 기본 행동** (레벨 미선언/하위 레벨 시):
- 한 스텝씩 진행하고, 사용자와 같이 확인한 뒤 다음으로 넘어간다
- L0: 파일 1개 수정/생성 후 사용자 확인 대기. L1: Task 단위로 묶어 보고
- 연관된 파일이라도 가능하면 나눠서 보여주기
- task를 만들어뒀더라도 한꺼번에 달리지 않기

**L2+ 선언 시**: 파일/Task 단위 확인 생략 — 대신 레벨 게이트(계획 승인 → 완료 리뷰)에서 검토. 검토 가능성은 구조로 보장 (Task별 커밋 + 완료 리포트 + 독립 리뷰).

**Why:** 이 원칙의 본질은 "속도 제한"이 아니라 **"검토 불가능한 덩어리 금지"**다. 여러 파일을 한꺼번에 고치면 검토 힘들고 되돌리기 어려웠던 경험에서 나옴 (실제로 위반하여 제지당함). L2+ 에서도 이 본질은 유지된다 — 확인 시점만 파일에서 산출물 경계로 승격.

## 코드 변경
- L0~L1: 코드 변경/파일 생성 전에 내용을 보여주고 확인 받은 후 진행
- L2+: 명세(sprint{N}.md) 승인이 사전 확인을 대체. 명세 밖 변경이 필요해지면 중단 + 보고 (supervision 불변 원칙 4)

## Git 커밋/푸쉬
- **푸쉬(push)는 모든 레벨에서 반드시 먼저 물어보고 승인 후 실행** — 절대 생략 금지 (과거 위반 — 반복 금지)
- 커밋: L0~L1 은 승인 후, L2+ 는 작업 브랜치 내 자동 커밋 허용 (명세에 정의된 커밋 메시지 사용)
- 빌드가 성공하고 실행까지 문제없는 상태가 확인된 후에만 커밋/푸쉬 제안

## Sprint 리뷰 프로세스
- Sprint가 끝나면 **사용자가 직접 화면을 확인하고 동작을 테스트**할 수 있는 상태여야 한다
- 빌드 오류 없음 + 실행 가능 + 눈으로 확인 가능한 상태가 최소 조건
- Sprint 완료 후 사용자 리뷰 시간을 반드시 갖는다 (수정 사항 반영)
- 사용자가 "확인 완료"할 때까지 다음 Sprint로 넘어가지 않는다 (L0~L2. **L3 선언 시에만** 스프린트 경계 자동 통과 — Phase 통합 리뷰가 게이트)

### 리뷰 시 발견된 이슈 분류
| 분류 | 처리 | 기록 위치 |
|------|------|-----------|
| 즉시 수정 | 리뷰 중 바로 고침 | - |
| 다음 Sprint | 바로 다음 Sprint 명세에 추가 | docs/sprint/sprint{N+1}.md |
| 나중 Sprint | 해당 Sprint 또는 백로그에 기록 | ROADMAP.md 또는 해당 sprint 명세 |

### 리뷰 단위
1. **Sprint 리뷰**: 매 Sprint 완료 시 실행 → 테스트 → 이슈 분류 → 수정/기록
2. **Phase 리뷰**: Phase(여러 Sprint 묶음) 완료 시 전체 플로우 통합 점검 + 다음 Phase 방향 재확인

**Why:** 리뷰 없이 다음으로 넘어가면 이슈가 누적되고 나중에 수습 불가. Sprint/Phase 단위로 끊어서 확인해야 품질 유지됨.

## 코딩 시 rules 적용
- 코드를 작성하기 **전에** rules/{tech}.md 핵심 규칙을 다시 읽는다
- 코드를 작성하는 **중에** 시니어 개발자처럼 코드 컨벤션을 자연스럽게 적용한다 (하드코딩, 네이밍, 타입, 구조, import 등 전부)
- 코드를 작성한 **후에** rules 원본과 대조하여 위반 사항을 수정한다
- "동작하면 됐지" 마인드 금지 — rules 위반 코드는 동작해도 수정한다

**Why:** 규칙을 만들어놓고 코딩할 때 안 지킨 적 있음. 사용자에게 지적당함. 특정 규칙만 체크하는 게 아니라 전체 코드 품질을 시니어 수준으로 유지해야 함.

## 보안 — 작업 중 상시 체크
- 보안은 한 번 점검하고 끝나는 게 아니라 **작업할 때마다 능동적으로 검증**한다
- sprint-workflow.md의 보안 원칙 + 해당 기술 rules/{tech}.md의 보안 섹션을 함께 따른다
- 문제 발견 시: 즉시 사용자에게 알리고 수정 제안 (다음 스프린트로 미루지 않는다)
- 기술별 구체 보안 사항은 rules 파일에, 여기는 "상시 체크해야 한다"는 행동 원칙만 기록

**Why:** 보안은 한 시점의 체크가 아니라 지속적 프로세스. 기능이 늘어날수록 공격 면도 늘어남.

## 품질
- 문서/코드 작성 시 항상: 상세하고, 꼼꼼하고, 있어보이게, 베스트 프랙티스로 작성
- 바이브 코딩 시 더 좋은 결과가 나오도록 고민하며 작성 (매번 말하지 않아도 기본 원칙)
